## 1. 功能與頁面範圍

### 1.1 功能範圍

**功能目的：** 定案並建立 Pokémon Gym v1「零 DB 靜態同步」資料層，以離線同步的 Pokémon GO 全實裝圖鑑靜態資料取代既有暫用假資料（`mock-roster.ts`），消除手機端執行期直打外部 API 的延遲與不穩定風險；同時將道館相剋引擎與畫面標籤升級為 Pokémon GO 專屬屬性倍率、GO 數值排序與 5 級中文效果文字，讓道館實戰玩家在手機上能即時、精準地查詢守衛並取得進攻推薦。

**包含範圍：**

- **正式靜態圖鑑資料來源**：建立離線資料同步腳本，合併 `pvpoke/pvpoke` 與 PokéAPI GraphQL v1beta2 資料，產出確定性排序的精簡靜態寶可夢資料檔（含基礎型態、四大地區型態與 GO 專屬數值），完全移除 `src/app/_mock/mock-roster.ts`。
- **首頁 `/` 圖鑑載入與搜尋**：首頁道館對戰分析工作區改由正式靜態資料載入完整圖鑑（900+ 筆），守衛選擇彈窗支援以繁體中文名稱（含地區型態前綴）、英文名稱與屬性關鍵字即時過濾搜尋。
- **Pokémon GO 相剋引擎升級**：將屬性相剋倍率改為 Pokémon GO 規則（單剋 `1.6`、雙剋 `2.56`、普通 `1.0`、單抗 `0.625`、雙抗／原作免疫屬性 `0.390625`、三抗 `0.244140625`，無 `0x` 完全免疫），並依覆蓋守衛數、相剋強度、`baseAttack`（主）與 `maxCp`（輔）由高至低排序推薦打手。
- **5 級中文效果標籤顯示**：畫面上所有相剋標籤（連線 pill、節點 badge、反打風險提示等）一律顯示 5 級中文文字（`雙重絕佳`、`效果絕佳`、`效果普通`、`效果不太好`、`效果極差`），不顯示 `2x`、`4x`、`1.6x` 等數字倍率。
- **圖片多層降級（Fallback）**：同步期依序嘗試 `official-artwork`、`home` 與原種 `dexId` 圖資；前端維持 `PokemonSprite` 載入失敗時的佔位圖示降級。
- **自動化每週資料同步流程**：建立 GitHub Actions 每週排程與手動觸發 workflow，上游資料有變動時自動建立 PR，無變動時不產生變更；同步失敗時保留既有可用靜態檔。
- **正式資料層規範文件**：更新 `docs/data-layer-guide.md`，由「待定案」改為正式資料層架構、同步流程與型別契約規範。

**不包含範圍：**

- 分離式後端服務與 Next.js `src/app/api/` Route Handlers
- Firebase、Supabase 或其他執行期（runtime）資料庫建置（亦不啟用 `src/legacy-backup/firebaseConfig.jsx`）
- 使用者登入、帳號系統、個人寶可夢背包與收藏隊伍管理
- 依可學招式（快速／蓄力招式、DPS／TDO）進行進攻推薦
- 超級進化（Mega）、原始回歸（Primal）、暗影（Shadow）與非地區型多戰鬥型態收錄
- `/pokedex` 獨立圖鑑頁之功能實作

## 2. 使用情境

### 2.1 情境一：開啟首頁載入正式靜態圖鑑並進行道館配對

**流程說明：** 玩家開啟首頁 `/` 後，系統直接由隨專案打包的正式靜態圖鑑載入完整 Pokémon GO 寶可夢清單，並在無任何外部 API 阻塞下顯示工作區。

**前置條件：**

- 靜態寶可夢資料檔已透過同步腳本產出並隨應用程式建置。
- 玩家使用支援的瀏覽器（iOS Safari、Android Chrome 或桌面瀏覽器）開啟網站。

**觸發操作：**

- 玩家直接造訪 `/` 或帶有 `?d=<id1>,<id2>` 的分享連結。

**主要流程：**

```
玩家開啟首頁 /
  │
  ├─> 系統直接讀取靜態圖鑑資料（零外部 API 請求）
  │
  ├─> 檢查 URL 查詢參數 `?d=`
  │   ├─> 無 `?d=` 或所有 ID 皆無效：顯示空白守衛槽位與引導新增畫面
  │   └─> 含有效守衛 ID（最多 6 隻、去重）：顯示守衛槽位列與對應的相剋連線舞台
  │
  └─> 玩家可立即點擊新增守衛、調整清單或操作連線畫布
```

**成功結果：**

- 首頁在無外部圖鑑 API 請求等待的情況下完成顯示。
- `?d=` 中符合靜態圖鑑 `id` 的守衛皆能正確還原（含基礎型態與地區型態）。

**失敗結果與復原方式：**

- 若網址 `?d=` 含有不存在、拼寫錯誤或已不支援的寶可夢 `id`：系統自動忽略無效項目，僅保留有效守衛；若過濾後無任何有效守衛，畫面回到「空資料」引導狀態，玩家可重新點擊「新增」挑選。
- 若因非預期異常導致工作區處於錯誤狀態：畫面顯示錯誤提示與「重試」按鈕，點擊重試可清除異常狀態並重新呈現目前有效的分析結果。

**適用的畫面狀態：**

- 初始／空資料（無守衛）、成功（已顯示推薦分析）、錯誤（異常狀態提示與重試）。

**使用場景：**

1. **初次進入道館前**：玩家站在道館前開啟 `/`，準備輸入眼前的守衛陣容。
2. **透過分享連結進入**：玩家開啟隊友分享的 `/?d=blissey,dragonite,metagross` 網址，直接查看分析結果。
3. **重新整理頁面**：玩家於查看推薦過程中重新整理瀏覽器，原有守衛陣容不遺失。

**業務規則與限制：**

- 靜態圖鑑僅收錄 Pokémon GO 已實裝（`released === true`）之基礎型態與四大地區型態（阿羅拉、伽勒爾、洗翠、帕底亞），且每座道館守衛上限為 6 隻、不可重複同一個 `id`。

**SD 設計提示：**

- 需設計靜態資料檔在 Server／Client Component 間的載入與傳遞邊界，避免不必要地放大初始 HTML／JS bundle 或造成多次序列化複製。
- 移除 `mock-roster.ts` 後，若仍保留範例載入動作，需確保範例 ID 與正式靜態資料 `id` 一致。

### 2.2 情境二：搜尋並挑選守衛寶可夢（含地區型態與多語系）

**流程說明：** 玩家開啟守衛選擇彈窗，透過繁體中文名稱、地區型態名稱、英文名稱或屬性關鍵字從 900+ 筆圖鑑中快速篩選並挑選 1～6 隻道館守衛。

**前置條件：**

- 玩家位於首頁 `/`。
- 守衛選擇彈窗已開啟。

**觸發操作：**

- 玩家點擊空守衛槽位或舞台「新增」按鈕開啟彈窗，並於搜尋欄輸入關鍵字或點擊寶可夢卡片。

**主要流程：**

```
玩家開啟守衛選擇彈窗
  │
  ├─> 彈窗顯示目前草稿已選數量（0～6 / 6）與完整圖鑑列表
  │
  ├─> 玩家於搜尋框輸入關鍵字（繁中名／地區型態前綴／英文名／屬性名）
  │   ├─> 即時過濾清單並顯示符合的寶可夢卡片（圖片、繁中名稱、屬性標籤）
  │   └─> 若無符合項目：顯示「找不到符合『關鍵字』的寶可夢」空狀態與清除搜尋操作
  │
  ├─> 搜尋框下方顯示「已選守衛圖片列」（已選數量 >= 1 時呈現，顯示已選寶可夢縮圖與 `×` 移除鈕）
  │   └─> 玩家即使已捲動至清單深處或正在搜尋其他寶可夢，仍可一鍵點擊 `×` 取消已選守衛
  │
  ├─> 玩家點選或取消點選卡片（上限 6 隻；達上限時未選卡片停用）
  │
  └─> 玩家點擊「完成」確認送出
      └─> 關閉彈窗、更新守衛槽位、更新 URL `?d=` 並重新計算相剋推薦
```

**成功結果：**

- 輸入「阿羅拉」、「臭臭泥」、「Muk」、「alola」或屬性「毒」、「惡」等皆能準確篩選出對應的「阿羅拉臭臭泥」等目標寶可夢。
- 點擊確認後，守衛清單與相剋舞台即時更新，無額外等待。

**失敗結果與復原方式：**

- **搜尋無結果**：顯示明確查無結果提示，玩家可點擊搜尋框右側「清除搜尋」按鈕或修改關鍵字立即恢復清單。
- **圖鑑卡片圖片載入失敗**：該張卡片改以佔位圖示呈現，不影響寶可夢名稱、屬性標籤顯示與點選功能。
- **取消操作與搜尋重置**：玩家關閉守衛選擇彈窗（無論點擊「完成」或取消關閉）時，系統自動清空搜尋關鍵字 `searchQuery` 為 `""`，確保下次開啟彈窗時顯示完整圖鑑而非停留在前次搜尋或空結果狀態；未按確認即關閉彈窗時維持原守衛清單。

**適用的畫面狀態：**

- 成功（顯示清單）、空資料（搜尋查無結果或圖鑑清單為空）、停用（已選滿 6 隻時其餘未選卡片不可點擊）。

**使用場景：**

1. **辨識地區型態守衛**：玩家在道館看到「阿羅拉臭臭泥」或「伽勒爾雙彈瓦斯」，輸入「阿羅拉」或「伽勒爾」快速鎖定正確屬性組合。
2. **以英文名稱搜尋**：習慣英文譯名的玩家輸入「Dragonite」或「Tyranitar」搜尋。
3. **以屬性關鍵字搜尋**：玩家輸入「龍」或「鋼」瀏覽該屬性所有可選守衛。
4. **搜尋錯字後修正**：輸入無結果關鍵字後，點擊清除按鈕重新輸入。

**業務規則與限制：**

- 搜尋比對範圍包含：`zhName`（繁體中文名稱，地區型態含明確前綴如「阿羅拉臭臭泥」）、`enName`（英文名稱，不分大小寫）、`id` 與 `types`（英文屬性 ID 與繁中屬性名稱）。
- 草稿清單最多選擇 6 隻，已選滿 6 隻時未選卡片進入停用狀態，已選卡片與搜尋框下方已選縮圖列仍可點擊取消。
- 即使清單採虛擬視窗或搜尋過濾隱藏了先前勾選的卡片，已勾選狀態仍完整保留於草稿清單，不會因捲動卸載而被取消。

**SD 設計提示：**

- 靜態圖鑑擴增至 900+ 筆後，需於 SD 階段評估彈窗列表的渲染效能（如避免一次掛載過多節點或圖片請求擁塞，同時確保搜尋過濾即時流暢）。

### 2.3 情境三：檢視 Pokémon GO 相剋推薦、5 級中文標籤與反打風險

**流程說明：** 玩家選定守衛後，於相剋連線舞台檢視依 Pokémon GO 屬性倍率與 GO 數值排序的推薦進攻打手，並透過 5 級中文效果標籤與反打風險標示做出派兵決策。

**前置條件：**

- 至少已選擇 1 隻有效守衛寶可夢。

**觸發操作：**

- 確認守衛選擇後自動計算，或點擊舞台上的攻擊方／防守方節點聚焦檢視特定連線。

**主要流程：**

```
系統依已選守衛執行 Pokémon GO 相剋計算
  │
  ├─> 篩選候選打手（排除已在守衛清單中的寶可夢）
  │   ├─> 計算我方對各守衛最佳同屬性進攻倍率（GO 倍率：1.6 / 2.56 / 1.0 / 0.625 / 0.390625 / 0.244140625）
  │   └─> 計算守衛對我方反打倍率（GO 倍率，達 1.6x 以上標記為反打風險）
  │
  ├─> 依多守衛覆蓋數、相剋強度、baseAttack（主）與 maxCp（輔）排序並取前 4 名推薦打手
  │
  ├─> 繪製相剋連線舞台
  │   ├─> 連線 pill 與節點 badge 顯示進攻屬性名稱 + 5 級中文效果文字（如「雙重絕佳」、「效果絕佳」）
  │   ├─> 若開啟顯示風險且存在反打風險：顯示虛線風險連線與 5 級中文風險標籤（如「反打 效果絕佳」）
  │   └─> 若有守衛未被任何推薦打手覆蓋：於舞台上方／節點顯示未覆蓋警示
  │
  └─> 玩家可點擊節點鎖定檢視單一或多重對位細節，或點擊「顯示全部連線」恢復總覽
```

**成功結果：**

- 所有推薦打手皆符合 Pokémon GO 相剋規則（不再出現原作 `2x`、`4x` 或 `0x` 無效判斷）。
- 相同覆蓋數與相剋等級下，攻擊力（`baseAttack`）與 Lv50 `maxCp` 較高的實用打手排在前面。
- 畫面上所有相剋標籤一律以 5 級中文文字呈現，玩家無需換算倍率數字即可直覺判斷優勢與風險。

**失敗結果與復原方式：**

- **部分守衛未被覆蓋**：舞台持續顯示已覆蓋的推薦打手，並以琥珀色提示條與虛線外框明確標示未被覆蓋的守衛名稱，提示玩家手動留意。
- **無任何打手可覆蓋目前守衛**（例如極端條件下無符合門檻之推薦）：舞台守衛節點均標示為未覆蓋並顯示未覆蓋提示，玩家可調整守衛清單。

**適用的畫面狀態：**

- 成功（顯示連線舞台與 5 級中文標籤）、局部警告（含未覆蓋守衛提示）。

**使用場景：**

1. **判斷雙重弱點速攻**：面對「快龍」（龍／飛行）或「暴鯉龍」（水／飛行），玩家看到冰系或電系推薦並標示「雙重絕佳」，優先派出該屬性打手。
2. **確認無免疫機制**：面對「幸福蛋」（一般）或「耿鬼」（幽靈／毒），系統依 GO `0.390625` 雙抗規則正確計算而非當作 `0x` 完全免疫。
3. **避開高風險反打**：玩家點選推薦打手後，看到守衛對該打手有「反打 效果絕佳」提示，可改選其他較安全的推薦打手。

**業務規則與限制：**

- 嚴禁在畫面上顯示 `2x`、`4x`、`1.6x`、`2.56x`、`0x` 等數字倍率，一律轉換為 5 級中文標籤。
- 推薦進攻打手排除目前已被選為敵方守衛的同一隻寶可夢 `id`。

**SD 設計提示：**

- 需將 `type-chart.ts`、`matchup-engine.ts` 與 `graph-layout.ts` 中的 `counter-2x` / `counter-4x` 語意及 `>= 2` / `>= 4` 門檻重構為符合 Pokémon GO 5 級效果的型別與計算邏輯。

### 2.4 情境四：執行離線資料同步腳本與每週自動同步 PR（維運流程）

**流程說明：** 專案維運者透過手動指令或 GitHub Actions 每週排程執行離線同步腳本，合併 `pvpoke/pvpoke` 與 PokéAPI GraphQL v1beta2 資料產出最新靜態圖鑑；遇上游異常時中止寫入以保護既有可用資料。

**前置條件：**

- 執行環境具備網路連線以存取 `pvpoke/pvpoke`（GitHub raw JSON）與 PokéAPI GraphQL v1beta2（`https://graphql.pokeapi.co/v1beta2`）。
- 專案儲存庫中已存在（或首次建立）目標靜態資料輸出路徑。

**觸發操作：**

- 維運者於本機終端機執行同步指令（如 `pnpm sync:pokemon`），或 GitHub Actions 依每週 `schedule`／手動 `workflow_dispatch` 自動觸發。

**主要流程：**

```
觸發離線同步腳本
  │
  ├─> 向上游取得資料：
  │   ├─> 1. 下載 pvpoke/pvpoke gamemaster pokemon.json（取得 released、tags、baseStats、types 等）
  │   └─> 2. 查詢 PokéAPI GraphQL v1beta2（language_id = 4 繁中名稱、圖片 URL）
  │
  ├─> 驗證上游回應狀態與資料 Schema 完整性
  │   ├─> 若發生逾時、HTTP 錯誤或 Schema 異常：
  │   │   └─> 印出明確錯誤訊息、以非零結束碼中止，且「不覆寫」既有靜態資料檔
  │   └─> 若驗證通過：繼續處理
  │
  ├─> 執行過濾、映射與數值計算：
  │   ├─> 僅保留 released === true 之基礎型態與四大地區型態（alolan/galarian/hisuian/paldean）
  │   ├─> 排除 shadow、mega、primal 與非地區型多戰鬥型態
  │   ├─> 執行地區型態 slug 對應與圖片多層降級（official-artwork → home → 原種 official-artwork 並印 warning）
  │   ├─> 依官方 Lv50 CPM 公式計算 maxCp
  │   └─> 依 dexId + form 進行確定性排序
  │
  └─> 寫入精簡靜態資料檔
      └─> （若為 GitHub Actions）檢查 git diff：
          ├─> 有變動：自動建立 PR（不直接 push main）
          └─> 無變動：結束任務，不建立 PR
```

**成功結果：**

- 本機產出確定性排序的靜態寶可夢資料檔，每筆具備完整必要欄位，且每個變更 PR diff 乾淨可審查。
- 每週排程在資料有更新時自動開啟 PR 供審查合併。

**失敗結果與復原方式：**

- **上游 API 逾時、HTTP 非 2xx 或 Schema 缺漏／異常**：腳本立即失敗並輸出失敗原因，**既有靜態資料檔完整保留不受破壞**，線上與本機建置仍可正常運作；維運者可於上游恢復後重新執行同步指令或手動重跑 `workflow_dispatch`。
- **部分地區型態缺圖**：依降級規則改採 `home.front_default` 或原種 `dexId` `official-artwork` 並於同步 log 印出 warning，不中斷整體同步。

**適用的畫面狀態：**

- 不適用（此情境為離線 CLI 腳本與 CI 工作流程，不直接渲染前端畫面狀態）。

**使用場景：**

1. **版本初始化／手動更新圖鑑**：新世代或新地區型態於 Pokémon GO 實裝後，開發者執行同步腳本更新靜態資料。
2. **每週定期自動同步**：GitHub Actions 每週自動檢查上游是否有新實裝寶可夢或數值調整並開立 PR。
3. **上游服務暫時維護中斷**：PokéAPI GraphQL 暫時逾時時，腳本安全中止而不覆寫既有正式靜態檔。

**業務規則與限制：**

- 嚴格遵守「禁止直接 push `main`」規範，GitHub Actions 僅能使用最小權限建立 PR。
- 同步產物僅保留前端所需之精簡欄位，以確保壓縮後體積與執行期載入效能。

**SD 設計提示：**

- 需定義靜態資料檔的存放路徑、格式（JSON 或 TS 模組）、與前端共用的型別契約，以及 Lv50 CPM 計算常數與 `pvpoke` tags／`dex` 對應規則。

### 4.2 狀態轉換

| 目前狀態 | 觸發事件 | 進行中狀態 | 成功後 | 失敗或取消後 |
| -------- | -------- | ---------- | ------ | ------------ |
| 空資料（舞台） | 開啟彈窗並選取守衛點擊「完成」 | 本地同步計算（無網路等待） | 進入「成功」狀態，更新 URL `?d=` 與相剋連線舞台 | 點擊彈窗外或取消關閉則維持「空資料」 |
| 成功（舞台就緒） | 於彈窗修改守衛或移除單一守衛 | 本地同步計算（無網路等待） | 若剩餘 ≥ 1 隻則更新連線舞台；若歸零則轉為「空資料」 | 若僅無推薦打手覆蓋，仍維持「成功」並於未覆蓋守衛顯示警示 |
| 搜尋顯示清單 | 輸入無符合項目之關鍵字 | 即時過濾（無網路等待） | 進入「空資料（搜尋無結果）」狀態，保留草稿已選清單 | 點擊「清除搜尋」後恢復顯示完整清單並保留已選項目 |
| 錯誤（舞台） | 點擊「重試」 | 清除錯誤旗標並重新評估狀態 | 依目前 `?d=` 有效守衛進入「成功」或「空資料」 | 若資料仍異常則維持「錯誤」並保留重試入口 |

### 4.3 狀態適用原則

- 本功能採「零 DB 靜態同步」架構，首頁開啟與搜尋皆不發送執行期外部 API 請求，因此正常操作下不會出現長時間網路阻塞的載入失敗，但仍保留 `<Suspense>` 與既有錯誤復原介面以維持系統強健性。
- 明確區分「搜尋查無結果（成功讀取靜態清單但篩選為 0 筆）」與「舞台錯誤（無法取得資料或異常）」；前者保留草稿選取狀態並提供清除搜尋，後者提供重試入口。

## 5. 使用者流程圖

### 5.1 首頁進入與道館對戰分析主流程

```
使用者開啟首頁 /（或帶 ?d= 參數）
  │
  ├─> 直接讀取靜態寶可夢圖鑑資料（無外部 API 請求）
  │
  ├─> 解析與驗證 URL `?d=` 守衛清單（上限 6 隻、去重）
  │   ├─> 無有效守衛：顯示「空資料」引導畫面
  │   └─> 有 1～6 隻有效守衛：
  │       ├─> 依 Pokémon GO 倍率與 GO 數值計算推薦打手與反打風險
  │       └─> 顯示守衛槽位列與相剋連線舞台（含 5 級中文標籤）
  │
  └─> 使用者可點擊節點聚焦、調整畫布選項或點擊「新增」修改守衛
```

### 5.2 搜尋與挑選守衛流程（含地區型態與圖片降級）

```
使用者點擊空槽位或「新增」
  │
  ├─> 開啟守衛選擇彈窗（載入目前已選清單為草稿）
  │
  ├─> 使用者輸入搜尋關鍵字（繁中名／地區型態／英文名／屬性）
  │   ├─> 有符合項目：顯示候選卡片網格
  │   │   └─> 若單張圖片載入失敗：該卡片顯示佔位圖示，不影響名稱與選取
  │   └─> 無符合項目：顯示「找不到符合『關鍵字』的寶可夢」與清除鈕
  │
  ├─> 使用者勾選／取消勾選守衛（上限 6 隻）
  │
  └─> 使用者點擊「完成」
      ├─> 關閉彈窗
      ├─> 更新 URL `?d=` 並清除舊節點鎖定
      └─> 重新計算並更新相剋連線舞台
```

### 5.3 離線資料同步與每週自動開 PR 流程

```
觸發同步（手動 pnpm sync:pokemon 或 GitHub Actions 每週排程）
  │

      ├─> 無變動：結束流程
```

### 6.1 資料來源與用途

| 資料 | 來源 | 取得或更新時機 | 畫面用途 |
| ---- | ---- | -------------- | -------- |

| 守衛清單狀態（`?d=`） | 瀏覽器 URL Search Params | 進入頁面時解析；使用者新增、移除、清空或確認守衛選擇時更新 | 決定目前分析的守衛陣容，支援重新整理保留與網址分享 |
| 畫布顯示偏好 | 瀏覽器本地儲存偏好（既有 `useCanvasPreferences`） | 使用者開啟畫布選項彈窗調整設定時更新 | 控制名稱顯示、5 級中文標籤位置（連線 pill 或節點 badge）、風險連線顯示等 |

### 6.2 靜態資料欄位契約（SA 層業務定義）

依需求規格，每筆靜態寶可夢資料須具備以下可驗證欄位，供前端搜尋、展示與推薦計算使用：

| `zhName` | 繁體中文名稱（地區型態須具明確前綴，如「阿羅拉臭臭泥」） |
| `enName` | 英文名稱（用於搜尋比對） |
| `form` | 型態識別（基礎型態或 `alolan`／`galarian`／`hisuian`／`paldean` 等地區型態） |
| `types` | 屬性陣列（1 至 2 個 Pokémon GO 屬性） |

| `baseDefense` | Pokémon GO 基礎防禦力 |
| `baseStamina` | Pokémon GO 基礎耐力 |
| `maxCp` | 依 Pokémon GO 官方 Lv50 CPM 公式計算之最大 CP（用於推薦排序輔鍵） |

### 6.4 資料更新與畫面同步

- 使用者於守衛槽位列移除、清空，或於選擇彈窗點擊「完成」後，系統同步更新 URL `?d=` 並立即重算推薦打手與連線，畫面不需等待伺服器回應。
- 圖鑑資料本身的更新透過離線同步腳本與 GitHub Actions PR 合併部署完成，部署後使用者重新開啟或重新整理頁面即可取得最新圖鑑。

### 6.5 重新載入、失效與離開頁面

| 情境 | 資料處理與畫面結果 |
| ---- | ------------------ |
| 重新整理頁面 | 保留 URL `?d=` 與本地畫布偏好，重新載入後顯示完全一致的守衛與推薦分析結果；未確認的彈窗草稿與搜尋字串重置 |
| 切換搜尋關鍵字 | 即時從靜態圖鑑過濾，不清除彈窗內已勾選的草稿守衛清單 |
| 離開後返回頁面 | 若網址仍含 `?d=`，立即還原該陣容分析 |
| 離開頁面（彈窗開啟中） | 未點擊「完成」的草稿選擇不寫入 URL，不會污染已儲存的陣容 |

### 6.6 錯誤、重試與資料保留

| 失敗情境 | 畫面呈現 | 保留內容 | 復原方式 |
| -------- | -------- | -------- | -------- |
| 單張寶可夢圖片載入失敗 | 該位置顯示佔位圖示與屬性底色 | 保留該寶可夢名稱、屬性標籤與所有選取／分析功能 | 不阻斷操作；重新開啟或圖資恢復時重新載入 |
| URL `?d=` 含無效或重複 ID | 自動忽略無效／重複項，其餘正常顯示 | 保留所有合法且不重複的守衛（最多 6 隻） | 使用者可繼續新增或調整陣容 |
| 舞台進入錯誤狀態 | 舞台顯示錯誤提示與「重試」按鈕 | 保留 URL `?d=` 與槽位列（若有效） | 點擊「重試」清除錯誤狀態並重新計算 |

## 7. 業務規則與權限

### 7.1 業務規則

| 規則 | 適用條件 | 前端行為 | 不符合時的結果 |
| ---- | -------- | -------- | -------------- |
| Pokémon GO 屬性倍率表 | 所有進攻與防守相剋計算 | 嚴格採用 GO 倍率：單剋 `1.6`、雙剋 `2.56`、普通 `1.0`、單抗 `0.625`、雙抗／原作免疫屬性 `0.390625`、三抗 `0.244140625` | 禁止使用原作 `2x`/`4x`/`0x` 規則；原本 `0x` 免疫組合改計為 `0.390625`（或疊加另一抗性為 `0.244140625`） |
| 5 級中文效果標籤顯示 | 所有連線 pill、節點 badge 與反打風險提示 | 依倍率映射並顯示 5 級中文文字：`雙重絕佳`（`2.56`）、`效果絕佳`（`1.6`）、`效果普通`（`1.0`）、`效果不太好`（`0.625`）、`效果極差`（`0.390625`／`0.244140625`） | 畫面上嚴禁出現 `2x`、`4x`、`1.6x`、`½x`、`¼x`、`0x` 等數字或分數倍率 |
| 進攻覆蓋與推薦排序 | 守衛 ≥ 1 隻時計算推薦打手 | 1. 排除已在守衛清單中的寶可夢<br>2. 僅推薦至少對 1 隻守衛達「效果絕佳」（`1.6`）或「雙重絕佳」（`2.56`）的打手（取前 4 名）<br>3. 排序優先序：覆蓋守衛數（高→低）＞ 相剋綜合分數（`雙重絕佳 +3`、`效果絕佳 +1.5`，並保留反打風險 `incomingMultiplier >= 1.5` 扣分 `-0.5`）＞ `baseAttack`（高→低）＞ `maxCp`（高→低） | 若守衛未被任何推薦打手覆蓋，列為未覆蓋守衛並於畫面以虛線框與警示條提示 |
| 反打風險標示 | 顯示反打風險選項開啟時 | 若守衛自身屬性對推薦打手造成「效果絕佳」（`1.6`）或「雙重絕佳」（`2.56`），建立風險連線並標示 `反打 <5級中文標籤>` | 未達反打門檻者不顯示風險連線 |
| 圖鑑收錄與過濾規則 | 離線資料同步腳本執行時 | 僅收錄 `pvpoke` 中 `released === true` 之基礎型態與四大地區型態（`alolan`／`galarian`／`hisuian`／`paldean`） | 明確排除 `shadow`、`mega`、`primal` 與非地區型多戰鬥型態 |
| 地區型態 Slug 與圖資降級 | 離線資料同步映射地區型態時 | Slug 對應：`alolan`→`-alola`、`galarian`→`-galar`、`hisuian`→`-hisui`、`paldean`→`-paldea`（含帕底亞肯泰羅亞型）；圖片依序降級 `official-artwork` → `home` → 原種 `dexId` `official-artwork` | 若降級至備援圖資，於同步 log 印出 warning，仍正常收錄該寶可夢 |
| 守衛數量與不可重複限制 | 首頁選取道館守衛 | 每座道館最少 1 隻（開始分析）、最多 6 隻守衛，且同一個 `id` 不可重複選取 | 已選滿 6 隻時，選擇彈窗內未選卡片呈停用狀態不可再選 |

### 7.2 欄位與操作限制

| 欄位或操作 | 限制條件 | 不符合時的畫面回應 | 是否阻擋後續流程 |
| ---------- | -------- | ------------------ | ---------------- |
| 守衛選擇數量 | 0～6 隻（單一 `id` 不可重複） | 達 6 隻時停用其餘未選卡片；0 隻時確認後舞台顯示空狀態引導 | 達上限阻擋繼續新增，不阻擋取消與確認 |

| 畫布控制列操作 | 須有 1～6 隻守衛且舞台處於成功狀態 | 非就緒狀態下按鈕呈停用狀態不可點擊 | 僅停用畫布控制操作，不影響新增守衛 |

### 7.3 內容與操作可見性

| 角色或條件 | 內容呈現 | 操作狀態 | 說明 |
| ---------- | -------- | -------- | ---- |
