## 1. 概述

本文件規範了 專案的技術文件撰寫標準，確保所有文件具有一致性、可讀性和實用性。

### 1.1 文件撰寫目標

- ✅ **易於理解**：清晰、簡潔的語言，避免過度技術化的術語
- ✅ **結構一致**：統一的組織結構，方便讀者快速定位資訊
- ✅ **完整詳盡**：涵蓋所有必要資訊，包括範例、錯誤處理、使用情境
- ✅ **視覺友善**：使用表格、流程圖、代碼區塊等提升可讀性
- ✅ **可維護性**：明確的版本記錄，易於更新和追蹤變更

## 2. 文件結構規範

### 2.1 標準文件架構

所有前端 SD 文件應包含以下基本結構：

```markdown
# [功能名稱] SD 文件

> 文件頭部資訊

---

## 📋 目錄

---

## 1. 前端架構概述

- 功能目標與頁面範圍
- 主要 route、page、layout 與互動入口
- 重要設計決策與限制

## 2. Route、Page 與 Layout 設計

- route 結構
- page / layout / loading / error 責任
- 頁面進入、離開與導覽行為

## 3. Component 與 Server/Client 邊界設計

- component 分層與責任
- Server／Client Component 邊界與 `"use client"` 範圍
- props、事件處理與組合方式
- hook / lib / type 的拆分原則

## 4. 資料流與 API 串接設計

- 外部 API 契約來源
- request / response 對應到前端型別與畫面資料
- loading、empty、error、permission 等狀態處理

## 5. 狀態、錯誤與驗收對應

- local state / server state / URL state / form state
- 錯誤處理與復原方式
- 驗收條件對應與測試策略（選用）

---

## 版本歷史

---

© 版權聲明
```

### 2.2 章節編號規範

- **一級標題**：使用數字編號（例：`## 1. 概述`）
- **二級標題**：使用數字.數字編號（例：`### 2.1 傳輸協定`）
- **三級標題**：使用數字.數字.數字編號（例：`#### 2.1.1 HTTP 協定`）
- **最多不超過三層**：避免過深的層級結構

### 2.3 檔案命名規範

| 文件類型         | 命名格式                         | 範例                              |
| ---------------- | -------------------------------- | --------------------------------- |
| 功能 SD 文件     | `功能名稱-sd.md`（小寫+連字號）  | `course-management-sd.md`         |
| 前端整合設計文件 | `功能-整合類型.md`               | `checkout-payment-integration.md` |
| 指南類文件       | `主題-guidelines.md`             | `frontend-testing-guidelines.md`  |
| 架構設計文件     | `主題-architecture.md`           | `admin-routing-architecture.md`   |

## 5. 內容撰寫原則

### 5.1 語言風格

| 原則       | 說明                                 | ✅ 正確範例             | ❌ 錯誤範例                             |
| ---------- | ------------------------------------ | ----------------------- | --------------------------------------- |
| 使用現在式 | 描述系統行為使用現在式               | 伺服器會返回錯誤訊息    | 伺服器將會返回錯誤訊息                  |
| 主動語態   | 優先使用主動語態，清晰表達動作主體   | 客戶端發送請求          | 請求被客戶端發送                        |
| 簡潔明確   | 避免冗長的句子，每句話只表達一個概念 | 使用 JWT token 進行認證 | 系統使用 JWT token 來進行身份認證和授權 |
| 一致性術語 | 同一概念使用相同術語                 | 課程 (統一使用)         | 課程/堂/course 混用                     |

### 5.2 技術術語

**中英文混用規範：**

- 專有名詞首次出現時使用中英對照：`JSON Web Token (JWT)`
- 後續使用可只用縮寫：`JWT`
- 程式碼相關術語保持英文：`WebSocket`, `API`, `HTTP`, `REST`
- 一般性描述使用中文：「請求」、「回應」、「錯誤」

### 5.3 強調與提示

使用特定格式標示重要資訊：

**重要提示：**

```markdown
**注意事項：**

- API 回應的可預期錯誤應就地呈現於對應欄位或區塊
- 收到 401 錯誤時，應引導使用者重新登入
```

**警告訊息：**

```markdown
**IMPORTANT:** 當收到認證錯誤時，應立即停止所有操作並重新驗證。
```

## 6. 格式化規範

### 6.1 表格使用

**適用場景：**

- 欄位說明
- 參數列表
- 錯誤代碼對照
- 技術規格比較

**標準格式：**

```markdown
| 欄位名稱 | 類型   | 必填 | 說明                   |
| -------- | ------ | ---- | ---------------------- |
| `id`     | string | ✅   | 唯一識別碼 (UUID 格式) |
| `name`   | string | ✅   | 名稱                   |
| `email`  | string | ❌   | Email (可選)           |
```

**表格規範：**

- 使用 `✅` 表示必填，`❌` 表示選填
- 程式碼相關欄位名稱使用反引號：`` `id` ``
- 對齊使用連字號，確保可讀性
- 每個欄位都必須有清晰的說明

### 6.2 代碼區塊

**標準格式：**

```markdown
​`typescript
interface User {
  id: string;
  name: string;
}
​`
```

**語言標示規範：**

- TypeScript 介面定義：`typescript`
- JavaScript 代碼：`javascript`
- JSON 資料：`json`
- Shell 命令：`bash`
- 流程圖：不使用語言標示或使用 `text`

**範例片段要求：**

- 若提供實作片段，應保持語法正確
- 若只是設計片段，可使用簡化範例但需清楚標示用途
- 包含必要的註解說明
- 使用有意義的變數名稱
- 遵循專案的代碼風格規範

**TypeScript 註釋風格：**

在前端 SD 文件中的 TypeScript 型別定義，建議使用 JSDoc 風格的 `/** */` 註釋：

```typescript
// ✅ 正確：使用 JSDoc 風格
interface CourseListViewModel {
  /** 課程 ID */
  id: string;
  /** 課程標題 */
  title: string;
  /** 是否可上架 */
  canPublish: boolean;
}

enum CourseStatus {
  /** 草稿 */
  DRAFT = 'DRAFT',
  /** 已上架 */
  PUBLISHED = 'PUBLISHED',
}

// ❌ 錯誤：不要使用三斜線註釋
interface CourseListViewModel {
  /// 課程 ID
  id: string;
  /// 課程標題
  title: string;
}
```

### 6.3 清單格式

**無序清單：**

```markdown
- 第一項
- 第二項
  - 子項目 1
  - 子項目 2
```

**有序清單：**

```markdown
1. 第一步：建立連線
2. 第二步：發送請求
3. 第三步：處理回應
```

**核心特性清單（使用 emoji）：**

```markdown
- ✅ **清楚的畫面狀態**：明確區分 loading、empty、error 與 permission 狀態
- ✅ **完整的錯誤處理**：統一的 API 錯誤映射與使用者可見訊息
```

## 7. 前端架構與資料流規範

### 7.1 Route、Page 與 Layout 描述

每個受影響的前端 route 應說明：

```markdown
### [route path] - [頁面名稱]

**用途：** [此頁面支援的使用者任務]

**設計參考：** [Figma 或設計稿路徑，如 `docs/design/wireframes.md`，若無切版需求請標示不適用]

**檔案位置：**

- `src/app/.../page.tsx`
- `src/app/.../layout.tsx`（如適用）
- `src/app/.../loading.tsx`（如適用）
- `src/app/.../error.tsx`（如適用）

**頁面責任：**

- [資料取得或入口責任]
- [主要 UI 區塊]
- [導覽、權限或狀態處理]
- [page／layout 本身為 Server 或 Client Component；若需互動，`"use client"` 應下沉到子元件而非整頁]

**互動入口：**

| 操作 | 觸發來源 | 前端處理 | 後續結果 |
| ---- | -------- | -------- | -------- |
| ...  | ...      | ...      | ...      |
```

### 7.2 Component、Hook 與模組責任描述

此段落必須嚴格對應 SD 範本中的「3.3 元件責任明細」。請使用 `####` 作為各元件的標題，統一收攏結構，不可散落於 H3。

```markdown
#### [Component / Hook 名稱]

**類型：** page component / feature component / shared component / hook / lib

**元件復用與建立策略（UI 切版建議）：**

- 規劃 UI 實作時，必須**先查看共用元件是否有可以復用**（如 `src/components/` 或 `src/components/ui/`）。
- 若有，請明確標示「複用既有共用元件 `[元件名稱]`」。
- 若沒有可復用的元件，請明確給予 implementer 以下三種建立建議之一：
  1. **建立新的共用元件**：若預期會跨頁面/模組重複使用，建於 `src/components/`。
  2. **建立 co-location 元件**：若僅在當前路由使用且有拆分必要，建於 `app/<最深層的當前路由>/_components/`（例如：專屬 `[id]` 頁面的元件，應嚴格放在 `app/.../[id]/_components/`，不可提前提昇至父路由）。
  3. **單純不需要重複使用的元件**：直接 inline 實作於當前元件檔案內，不需額外抽離。

**渲染邊界：** Server Component（預設）/ Client Component

- 預設為 Server Component
- 標為 Client Component（`"use client"`）時，列出原因：事件處理、瀏覽器 API、client state 或互動 hook
- `"use client"` 應下沉到實際需要互動的最小子樹，避免整頁 client 化
- 不在此決定 data fetching 寫法（fetch／Server Action／TanStack／SWR 等未定案），只標明邊界與理由

**責任：**

- [此模組負責什麼]
- [此模組不負責什麼]

**輸入與輸出：**

| 項目 | 類型 | 說明 |
| ---- | ---- | ---- |
| props / params / return value | ... | ... |

**事件與副作用：**

- [使用者操作]
- [API 呼叫]
- [狀態更新]
- [導覽或外部跳轉]
```

### 7.3 資料流與 API 串接描述

> 🚫 **外部 API 契約不准腦補。** API path、method、欄位、enum、錯誤格式與狀態碼必須依據 Swagger/OpenAPI、SA、既有前端 API 呼叫程式碼或明確規格；找不到依據就標待澄清。
> SD 只描述前端如何呼叫、轉換、保存與呈現資料，不反向設計後端 API。

```markdown
### [資料互動名稱]

**契約來源：** Swagger/OpenAPI / SA / 既有程式碼 / 待澄清

**前端觸發時機：**

- [進入頁面時]
- [使用者操作時]
- [狀態變更時]

**資料流：**

1. [觸發來源]
2. [呼叫 API 或讀取資料]
3. [轉換為前端 view model]
4. [更新 state 或 UI]
5. [處理 loading / empty / error / permission]

**型別分類：**

| 類型 | 名稱 | 來源 | 用途 |
| ---- | ---- | ---- | ---- |
| API response type | ... | Swagger/OpenAPI | 描述外部 API 回應 |
| UI view model | ... | 前端轉換 | 畫面顯示資料 |
| Form values | ... | 表單設計 | 使用者輸入 |
| Component props | ... | Component 設計 | 元件輸入 |
| State shape | ... | 狀態設計 | 畫面或跨元件狀態 |
```

## 8. 範例與說明

### 8.1 設計範例原則

**可提供：**

1. **設計片段**：用於說明 component props、type、資料流或狀態轉換，不要求完整可執行
2. **多種畫面狀態範例**：成功、loading、empty、error、permission、disabled、submitting
3. **實際資料形狀範例**：使用接近 API 或畫面會出現的資料格式，避免無意義 placeholder

**範例結構：**

````markdown
#### 設計範例

**情境：** [描述此範例對應的使用者操作或畫面狀態]

​```typescript
type CourseListViewModel = {
  id: string;
  title: string;
  statusLabel: string;
  canPublish: boolean;
};
​```

**設計說明：**

- `statusLabel` 由 API status 轉換為畫面顯示文字
- `canPublish` 由權限與課程狀態共同決定
- 實作時應以既有 type / API client / component pattern 為準
````

### 8.2 錯誤與狀態範例

**功能涉及時可提供：**

- API 錯誤來源或狀態碼（若規格已知）
- 前端錯誤分類
- 使用者可見訊息
- UI 呈現位置（**必須遵循 `docs/style-guide.md` 規範**，例如：Table 空狀態必須指明使用 Card 元件實作）
- 復原或重試方式

```markdown
**1. 表單驗證錯誤：**

**觸發原因：** 使用者輸入缺少必填欄位或格式不符合規則

**前端處理：**

- 在對應欄位顯示錯誤訊息
- 保留使用者已輸入內容
- 禁止送出或在送出後回到可修正狀態

**復原方式：** 使用者修正欄位後可重新送出
```

## 9. 視覺化元素

### 9.1 流程圖

使用 ASCII 字元繪製前端互動或畫面狀態流程圖：

```markdown
​`
使用者進入課程列表頁
  │
  ├─> 檢查權限
  │   ├─> 無權限：顯示無權限狀態
  │   └─> 有權限：載入列表資料
  │
  ├─> 顯示載入狀態
  │
  ├─> API 回應
  │   ├─> 成功且有資料：顯示列表
  │   ├─> 成功但無資料：顯示 empty state
  │   └─> 失敗：顯示錯誤與重試操作
  │
  └─> 使用者操作
      ├─> 篩選 / 搜尋：更新 URL state 並重新取得資料
      └─> 點擊項目：導向詳情頁
​`
```

**流程圖規範：**

- 使用 `│`, `├─>`, `└─>` 等字元
- 清晰的縮排表示層級關係
- 每個步驟都要有明確的前端責任
- 複雜流程應包含 loading、empty、error、permission 等分支

### 9.2 時序圖

時序圖為選用，只在互動順序會影響實作判斷時使用，例如：多步驟提交、重試、輪詢、即時連線、第三方跳轉、避免競態或防止重複送出。

```markdown
​`
[使用者]              [Page]              [API Client]          [外部 API]
   │                    │                     │                    │
   ├─ 點擊送出 ────────>│                     │                    │
   │                    ├─ 設為 submitting ─>│                    │
   │                    │                     ├─ 發送請求 ───────>│
   │                    │                     │<──── 回應 ────────┤
   │                    ├─ 更新 UI 狀態 <────│                    │
   │<─ 顯示結果 / 錯誤 ─┤                     │                    │
​`
```

## 10. 版本控制

### 10.1 版本號規範

採用語意化版本號：`v[Major].[Minor]`

- **Major（主版本號）**：重大更新、破壞性變更
- **Minor（次版本號）**：新增功能、向後相容的修改

範例：

- `v1.0`：初版發布
- `v1.1`：新增功能或小幅修改
- `v2.0`：重大更新或架構變更

### 10.2 版本歷史表格

文件末尾必須包含版本歷史：

```markdown
---

**文件版本歷史：**

## 附錄 C：常見問題

### Q1: 何時應該建立新文件？

**A:** 在以下情況下應建立或更新獨立的前端 SD 文件：

- 新增獨立的前端功能、頁面或管理流程
- 新增或大幅調整 route、page、layout 或跨頁導覽
- 新增外部 API 串接、第三方服務、即時連線或外部跳轉流程
- 重要的前端架構設計、狀態管理、表單處理、權限呈現或錯誤處理決策

### Q2: 文件應該放在哪裡？

**A:** 遵循以下目錄結構：

- `docs/features/`：功能 SA / SD 文件
- `docs/changes/<change-id>/`：變更中的 SA / SD 草稿與執行文件
- `docs/`：指南、規範類文件
- `docs/architecture/`：跨功能架構設計文件（如需要）

### Q3: 如何處理多語言文件？

**A:** 目前專案以繁體中文為主：

- 保持技術術語的英文原文
- 重要的專有名詞首次出現時提供中英對照
- 代碼範例中的註解使用中文

### Q4: 文件更新頻率？

**A:**

- 功能新增或調整時：同步更新相關 SA / SD 文件
- Route、component、資料流、狀態、表單、權限或錯誤處理變更時：立即更新相關 SD
- 外部 API 契約、Swagger/OpenAPI 或整合方式變更時：更新資料流與 API 串接章節
- 定期審查：每季度檢視並更新過時內容
