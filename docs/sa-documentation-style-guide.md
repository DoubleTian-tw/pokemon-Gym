## 1. 概述

本文件規範前端系統分析（System Analysis）文件的撰寫標準，專注於功能與頁面範圍、使用者流程、UI 行為、畫面狀態、資料互動、業務規則與權限，作為後續 SD 技術設計與功能驗收的依據。

### 1.1 SA 文件撰寫目標

- ✅ **清晰的使用流程**：描述使用者從進入頁面、執行操作到完成或離開功能的流程，以及其中的導航與條件分支
- ✅ **明確的畫面行為**：定義各項操作對 UI 的影響，以及載入中、成功、空資料、錯誤、無權限等畫面狀態
- ✅ **完整的資料互動**：記錄使用者操作、前端狀態與外部 API／第三方服務之間的資料流向和互動結果
- ✅ **可驗證的業務規則**：說明業務條件如何影響畫面內容、操作權限、欄位限制與流程結果
- ✅ **實用的使用情境**：提供真實場景、前置條件、成功流程、失敗流程與復原方式
- ✅ **可供 SD 延伸的分析依據**：明確交代功能範圍、行為需求、限制與待澄清事項，供 SD 進一步設計前端架構與實作方式
- ✅ **易於維護更新**：使用標準化格式，便於後續修改、驗收與擴充

### 1.2 SA 文件的核心組成

SA 文件應依功能範圍包含以下核心元素：

1. **功能與頁面範圍**：說明功能目的、使用者角色、入口頁面、相關路由與導航結果
2. **使用情境**：描述前置條件、觸發操作、主要流程、成功結果、失敗結果與復原方式
3. **UI 組成與操作**：列出主要畫面區塊、顯示內容、操作入口及其行為
4. **畫面狀態**：描述初始、載入中、成功、空資料、錯誤、無權限、停用與提交中等適用狀態
5. **流程圖**：展示使用者操作、畫面回應、條件分支與流程結果
6. **時序圖（選用）**：外部 API、第三方服務、即時連線或複雜非同步互動的先後順序會影響畫面結果，且一般流程圖不足以表達時，展示其互動順序
7. **資料互動與生命週期**：描述資料的取得、顯示、更新、重新載入、失效及離開頁面時的處理
8. **業務規則與權限**：說明業務條件如何影響內容顯示、欄位限制、操作權限及流程結果
9. **即時連線與第三方服務（選用）**：功能涉及持續連線、外部跳轉、回呼、中斷、取消或恢復流程時，描述其生命週期與前端可見結果
10. **待澄清事項**：列出缺少依據、規格衝突或需由使用者確認的項目
11. **非功能性需求（選用）**：spec 或既有規範有明確要求時，記錄可驗收的效能、響應式、無障礙、瀏覽器支援或可靠性需求

## 2. 功能與頁面範圍

本章用於界定功能與頁面邊界，讓後續使用情境、SD 設計與驗收具有一致範圍。僅描述可確認的需求；未定內容應列入待澄清事項，不得自行擴張功能。

### 2.1 功能範圍

說明此功能要解決的問題、預期結果，以及本次變更包含與不包含的內容：

```markdown
**功能目的：** [此功能要解決的使用者問題與預期結果]

**包含範圍：**

- [本次需要提供的頁面、內容或操作]

**不包含範圍：**

- [已確認不在本次處理的內容]
```

### 2.2 使用者與進入方式

說明哪些使用者會使用此功能，以及如何進入相關頁面：

```markdown
| 項目 | 說明 |
| ---- | ---- |
| 適用角色 | [可使用此功能的使用者角色] |
| 入口頁面 | [使用者從哪個頁面開始] |
| 進入操作 | [點擊、選取或其他進入方式] |
| 直接網址進入 | [允許、限制或待確認] |
```

本節只描述已知的使用者與入口，不在此決定驗證、授權或路由保護的實作方式。

### 2.3 頁面與導航結果

列出功能涉及的頁面或 route，以及各操作完成後的導航結果：

```markdown
| 情境 | 起始位置 | 目標位置或結果 |
| ---- | -------- | ---------------- |
| 進入功能 | [入口頁面或 route] | [目標頁面或 route] |
| 操作成功 | [目前頁面] | [停留、導頁或返回結果] |
| 取消或返回 | [目前頁面] | [返回位置或保留狀態] |
| 重新整理 | [目前 route] | [重新載入後的預期結果] |
```

若 route 或導航結果尚未確定，應標記為 `[待澄清]`，不得自行建立路徑或推測行為。

## 3. 使用情境撰寫規範

### 3.1 情境結構

每個使用情境應包含以下標準結構：

```markdown
### [編號] 情境[編號]：[情境名稱]

**流程說明：** [用一句話概述使用者操作與預期結果]

**前置條件：**（如適用）

- [使用者角色、權限、目前頁面或必要資料狀態]

**觸發操作：**

- [使用者執行的操作或進入流程的方式]

**主要流程：**

​```
[描述使用者操作、畫面回應、資料互動與流程結果]
​```

**成功結果：**

- [操作完成後的畫面內容、狀態或導航結果]

**失敗結果與復原方式：**

- [失敗時的畫面回應]
- [重試、返回、取消或其他復原方式]

**適用的畫面狀態：**

- [載入中、成功、空資料、錯誤、無權限、停用或提交中等實際適用狀態]

**使用場景：**

1. [具體的使用場景 1]
2. [具體的使用場景 2]
3. [具體的使用場景 3]

**業務規則與限制：**

- [影響內容、操作、欄位或流程結果的規則]

**SD 設計提示：**（可選）

- [需要 SD 進一步設計的前端技術問題]
- [不得在 SA 中直接指定的實作方案或待決策事項]
```

### 3.2 情境命名規範

情境名稱應該：
- 清晰描述主要功能或操作
- 使用動詞開頭（例：建立、進入、發送、離開）
- 簡潔明確（5-10 個中文字）

**良好範例：**
- ✅ 情境一：建立課程
- ✅ 情境二：進入課程列表
- ✅ 情境三：編輯課程內容
- ✅ 情境四：上架課程
- ✅ 情境五：處理儲存失敗

**不良範例：**
- ❌ 情境一：課程
- ❌ 情境二：關於如何進入課程列表的流程
- ❌ 情境三：編輯

### 3.3 流程說明撰寫原則

**使用主動語態：**

```markdown
✅ 管理員修改欄位後，點擊儲存以更新課程內容
❌ 課程內容被管理員的儲存操作更新
```

**明確指出角色：**

```markdown
✅ 管理員進入後台後，開啟課程列表並查看既有課程
❌ 進入後台後，查看課程
```

**說明目的和結果：**

```markdown
✅ 管理員送出儲存後，畫面進入提交中狀態，成功後顯示更新結果
❌ 管理員送出儲存，然後發生一些事情
```

### 3.4 使用場景列舉

每個情境應列出 2-5 個具體的使用場景，說明何時會觸發此流程：

```markdown
**使用場景：**

1. **初次進入**：管理員首次開啟課程列表頁
2. **切換條件**：管理員切換搜尋或篩選條件
3. **重新整理頁面**：管理員刷新瀏覽器頁面
4. **操作失敗重試**：儲存或載入失敗後重新嘗試
```

### 3.5 SD 設計提示（可選）

若 SA 已確認行為需求，但前端技術方案仍需由 SD 決定，可記錄需要進一步設計的問題。此處不得直接指定元件拆分、狀態管理、API client 或套件選型。

```markdown
**SD 設計提示：**

- 需設計歷史資料與即時資料的合併及去重方式
- 需設計切換頁面或中斷連線時的狀態清理方式
- 需決定載入、失敗與重試行為如何在前端架構中落實
```

## 4. UI 組成與操作

本章用於定義畫面需要呈現的資訊與支援的使用者操作，讓 SD 能依據明確的 UI 行為需求進行技術設計。本章描述畫面責任，不等同於 React component 的拆分規格。

### 4.1 畫面區塊

列出功能涉及的主要畫面區塊、顯示目的、資料內容與顯示條件：

```markdown
| 畫面區塊 | 顯示目的 | 顯示資料或內容 | 顯示條件 |
| -------- | -------- | -------------- | -------- |
| [區塊名稱] | [此區塊協助使用者完成什麼] | [欄位、文字、列表或提示內容] | [何時顯示、隱藏或替換] |
```

畫面區塊應依使用者可辨識的功能區域描述，不得直接推定元件名稱、檔案位置或 component hierarchy。

### 4.2 操作入口與回應

列出使用者可執行的操作、觸發位置、可用條件，以及操作後的立即回應與最終結果：

```markdown
| 操作 | 觸發位置 | 可用條件 | 立即回應 | 最終結果 |
| ---- | -------- | -------- | -------- | -------- |
| [操作名稱] | [按鈕、欄位、選單或其他入口] | [啟用、停用或顯示條件] | [操作後立即呈現的狀態] | [成功、失敗或取消後的畫面結果] |
```

「立即回應」用於描述操作進行中的 UI 變化，例如提交中、防止重複操作或顯示處理狀態；「最終結果」則描述流程完成後的內容更新、提示、導頁或復原方式。

### 4.3 UI 規格邊界

SA 應定義：

- 畫面需要呈現的內容與資訊層級
- 各項內容的顯示條件
- 使用者可執行的操作與限制
- 操作期間及完成後的畫面回應

SA 不應直接決定：

- React component 的拆分方式與 component hierarchy
- 狀態存放位置或狀態管理方案
- UI、表單、通知、Modal 或 Table 套件選型
- CSS 實作方式、Design Token 或視覺細節

上述技術方案應由 SD 根據 SA 定義的行為需求、既有專案結構與已確認的架構決策進一步設計。

## 5. 畫面狀態與回應

本章用於定義不同條件下的畫面呈現、可用操作與復原方式，避免只描述正常成功流程，而遺漏等待、空資料、失敗或無權限等使用者可觀察的狀態。

### 5.1 畫面狀態矩陣

依功能實際需求列出適用的畫面狀態：

```markdown
| 狀態 | 進入條件 | 畫面呈現 | 可用操作 | 離開條件 |
| ---- | -------- | -------- | -------- | -------- |
| 初始 | [尚未開始互動或取得資料] | [初始內容或提示] | [可執行操作] | [觸發載入或操作] |
| 載入中 | [開始取得資料] | [載入期間的呈現] | [允許或停用的操作] | [取得成功或失敗] |
| 成功 | [資料取得或操作成功] | [成功內容或更新結果] | [後續可執行操作] | [再次操作或離開頁面] |
| 空資料 | [成功取得資料但結果為空] | [空狀態內容] | [建立、返回或重新查詢] | [資料出現或條件變更] |
| 錯誤 | [載入或操作失敗] | [錯誤內容與影響範圍] | [重試、返回或其他復原操作] | [重試成功、取消或離開] |
| 無權限 | [使用者不具備查看或操作權限] | [提示、隱藏內容或導航結果] | [允許的替代操作] | [權限改變或離開] |
| 停用 | [業務條件不允許操作] | [停用狀態與原因] | [仍可使用的操作] | [條件符合或離開] |
| 提交中 | [開始送出資料] | [處理中的畫面回應] | [允許或防止的操作] | [提交成功、失敗或取消] |
```

上表是候選狀態，不要求每個功能全部使用。只保留有需求依據且實際適用的狀態。

### 5.2 狀態轉換

對會影響操作結果或復原方式的重要狀態，記錄其轉換關係：

```markdown
| 目前狀態 | 觸發事件 | 進行中狀態 | 成功後 | 失敗或取消後 |
| -------- | -------- | ---------- | ------ | ------------ |
| [目前狀態] | [使用者操作或外部事件] | [等待期間狀態] | [成功後畫面或導航結果] | [失敗呈現、資料保留與復原方式] |
```

狀態轉換應說明使用者輸入或既有資料是否保留，以及重試時從哪個狀態繼續。

### 5.3 狀態適用原則

- 只記錄功能實際存在且有需求依據的狀態，不為了填滿模板增加不存在的情況
- 區分首次載入與局部資料更新，避免將整頁與單一區塊的等待狀態混為一談
- 區分空資料與載入失敗；空資料是成功取得但沒有結果，錯誤則是流程未完成
- 區分頁面級錯誤與局部操作錯誤，說明各自影響的內容與可用操作
- 錯誤狀態必須描述使用者可採取的復原方式，例如重試、返回、取消或重新登入
- SA 定義狀態的進入條件、畫面結果、可用操作與復原方式，不指定狀態儲存、元件、Skeleton、Toast、Dialog 或其他實作方案

## 6. 使用者流程圖繪製指南

使用者流程圖用於呈現使用者如何完成任務，以及畫面在操作、等待、成功與失敗時如何回應。流程應以前端可觀察的行為為主，必要時可標示外部 API 或第三方服務互動，但不展開伺服器、Service 或 Database 的內部處理。

### 6.1 流程圖的用途與視角

流程圖應依下列順序描述：

```text
使用者觸發操作
→ 畫面立即回應
→ 必要的資料互動
→ 成功、失敗或取消結果
→ 使用者可採取的後續操作
```

流程節點只保留會影響使用者操作、畫面狀態、資料結果、導航或復原方式的內容。

### 6.2 基礎使用者流程

**簡單的線性流程：**

```
使用者開啟課程列表
  │
  ├─> 畫面顯示載入狀態
  │
  ├─> 取得課程列表資料
  │
  ├─> 畫面顯示課程列表
  │
  └─> 使用者可搜尋、篩選或進入課程內容
```

### 6.3 成功、失敗與復原分支

流程涉及資料取得或送出時，應描述成功、失敗及可復原路徑：

```
使用者點擊「儲存」
  │
  ├─> 畫面進入提交中狀態
  │   └─> 防止重複送出
  │
  ├─> 成功情況：
  │   ├─> 顯示更新後內容
  │   └─> 提供後續操作或依需求導頁
  │
  └─> 失敗情況：
      ├─> 保留使用者輸入
      ├─> 顯示失敗原因
      └─> 允許重新送出或取消
```

### 6.4 多步驟與條件流程

多步驟、表單或條件式畫面應標示各階段的畫面結果與分支：

```
使用者進入課程編輯頁
  │
  ├─> 載入既有課程資料
  │   ├─> 成功：顯示可編輯內容
  │   └─> 失敗：顯示錯誤與重試操作
  │
  ├─> 使用者修改欄位
  │   ├─> 符合規則：允許送出
  │   └─> 不符合規則：顯示欄位錯誤
  │
  └─> 使用者送出
      ├─> 成功：更新畫面並顯示結果
      └─> 失敗：保留輸入並提供重試
```

### 6.5 流程圖繪製規範

**必須遵守的規範：**

1. **縮排一致**：使用 2 或 4 個空格的統一縮排
2. **對齊整齊**：同層級的項目應該對齊
3. **符號正確**：使用標準的 ASCII 符號
4. **描述清晰**：每個步驟都要有明確的說明
5. **視角一致**：以前端可觀察的操作、狀態與結果為主
6. **必要互動**：API、第三方服務或即時事件只在影響流程時標示，不展開其內部處理

**良好的縮排範例：**

```
✅ 正確：
步驟 1
  │
  ├─> 子步驟 1.1
  ├─> 子步驟 1.2
  └─> 子步驟 1.3

❌ 錯誤（縮排不一致）：
步驟 1
 │
├─> 子步驟 1.1
  ├─> 子步驟 1.2
└─> 子步驟 1.3
```

### 6.6 流程圖的複雜度控制

**單一流程圖的建議：**

- 最多 3-4 層深度
- 單一流程不超過 15-20 個步驟
- 如果流程過於複雜，考慮拆分成多個小流程圖

**拆分範例：**

```markdown
### 主流程

​```
完整的業務流程
  ├─> 步驟 1: 進入頁面（詳見「進入頁面流程」）
  ├─> 步驟 2: 編輯內容（詳見「編輯內容流程」）
  └─> 步驟 3: 送出結果（詳見「送出結果流程」）
​```

### 進入頁面流程

​```
[詳細的頁面載入與錯誤復原流程]
​```

​```

​```

## 7. 時序圖繪製指南（選用）

時序圖用於展示多個角色依時間順序進行的互動。一般線性 UI 操作優先使用第 6 章的使用者流程圖；只有當外部 API、第三方服務、即時事件或複雜非同步順序會影響前端結果時，才需要時序圖。

### 7.1 基本時序圖結構

基礎時序圖可先用使用者與前端畫面說明操作和畫面回應：

```
[使用者]                    [前端畫面]
   │                           │
   ├─── 點擊操作 ───────────────>│
   │                           │ (更新畫面狀態)
   │<──── 顯示結果 ──────────────┤
   │                           │
```

### 7.2 標準符號說明

| 符號       | 用途         | 說明                                                   |
| ---------- | ------------ | ------------------------------------------------------ |
| `[角色]`   | 參與角色標題 | 例如使用者、前端畫面、外部 API、第三方服務或即時服務 |
| `│`        | 生命線       | 表示角色在互動時序中的存在時間                         |
| `├───>`    | 傳出互動     | 使用者操作、前端請求或送往外部服務的事件               |
| `<────┤`   | 傳回互動     | API 回應、外部事件或前端呈現給使用者的結果             |
| `(狀態)`   | 狀態標示     | 標示載入中、提交中、等待事件或其他重要畫面狀態         |

### 7.3 多角色時序圖

**三方互動範例：**

```
[使用者]              [前端畫面]              [外部 API]
   │                       │                       │
   ├─── 開啟課程列表 ─────>│                       │
   │                       │ (顯示載入狀態)         │
   │                       ├─── 取得課程列表 ──────>│
   │                       │<──── 課程資料 ─────────┤
   │                       │ (更新列表內容)          │
   │<──── 顯示課程列表 ────┤                       │
   │                       │                       │
```

### 7.4 包含畫面狀態的時序圖

**顯示處理狀態：**

```
[使用者]              [前端畫面]              [外部 API]
   │                       │                       │
   ├─── 點擊儲存 ─────────>│                       │
   │                       │ (進入提交中狀態)        │
   │                       ├─── 送出更新請求 ───────>│
   │                       │                       │ (處理中)
   │                       │<──── 更新成功 ──────────┤
   │                       │ (顯示更新後內容)         │
   │<──── 顯示成功結果 ────┤                       │
   │                       │                       │
```

### 7.5 複雜非同步與即時事件時序圖

當 API 回應與即時事件的抵達順序會影響畫面時，應標示前端等待和合併結果的順序：

```
[使用者]          [前端畫面]          [外部 API]          [即時事件服務]
   │                   │                   │                     │
   ├─── 開啟頁面 ─────>│                   │                     │
   │                   ├─── 取得初始資料 ─>│                     │
   │                   ├─── 開始監聽事件 ───────────────────────>│
   │                   │                   │                     │
   │                   │<──── 初始資料 ─────┤                     │
   │                   │ (顯示初始內容)      │                     │
   │                   │<──── 資料更新事件 ──────────────────────┤
   │                   │ (合併更新並重新呈現)│                     │
   │<──── 顯示最新結果 ─┤                   │                     │
```

### 7.6 錯誤與復原時序圖

**包含錯誤分支：**

```
[使用者]              [前端畫面]              [外部 API]
   │                       │                       │
   ├─── 點擊重新載入 ─────>│                       │
   │                       │ (顯示載入狀態)         │
   │                       ├─── 取得資料 ──────────>│
   │                       │<──── 請求失敗 ─────────┤
   │                       │ (顯示錯誤與重試操作)    │
   │<──── 顯示失敗原因 ────┤                       │
   ├─── 點擊重試 ─────────>│                       │
   │                       ├─── 再次取得資料 ──────>│
   │                       │<──── 取得成功 ──────────┤
   │<──── 顯示資料 ────────┤                       │
```

### 7.7 時序圖適用原則與繪製規範

**適用原則：**

- 一般線性操作或單純成功／失敗分支使用第 6 章流程圖即可
- 外部 API、第三方服務、即時事件或非同步順序會影響畫面結果時才使用時序圖
- 只呈現前端可觀察或必須回應的互動，不展開 Controller、Service、Database 等後端內部流程
- WebSocket、SSE 或第三方服務的完整生命週期另依第 10 章撰寫

**繪製規範：**

1. **角色對齊**：所有角色標題應該對齊
2. **生命線垂直**：每個角色的生命線（`│`）保持垂直
3. **箭頭方向**：請求向右（`───>`），回應向左（`<───`）
4. **時間順序**：從上到下表示時間流逝
5. **狀態標示**：重要的畫面狀態或等待階段用括號標示
6. **角色範圍**：優先使用使用者、前端畫面、外部 API、第三方服務或即時事件服務

**對齊範例：**

```
✅ 正確對齊：
[使用者]                    [前端畫面]                  [外部 API]
   │                           │                           │

❌ 錯誤對齊：
[使用者]     [前端畫面]    [外部 API]
   │           │          │
```

## 11. 待澄清事項

本章用於集中記錄會影響使用者流程、畫面行為、API 契約、權限或驗收結果，但現有依據不足或互相衝突的問題。不得用待澄清事項取代應由 SA 完成的分析，也不應把純技術實作選擇交由使用者決定。

### 11.1 需要列入待澄清的情況

符合下列任一情況時，應列入本章：

- spec、Swagger／OpenAPI、既有 SA 或前端程式碼的描述互相衝突
- API 路徑、Method、欄位、enum、狀態值或錯誤格式尚未提供
- 使用者操作後的畫面結果、導航位置或復原方式未定
- 角色、權限、內容可見性或禁止操作時的行為未定
- 業務規則會影響欄位、操作或流程結果，但缺少判斷依據
- 設計稿與文字需求不一致，且會影響功能行為或驗收

若問題只涉及 component 拆分、狀態管理、API client、套件選型或其他技術實作方式，應列為「SD 設計提示」，不列入本章。

### 11.2 待澄清事項格式

```markdown
| 編號 | 問題 | 已知依據與衝突 | 影響範圍 | 需要確認者 | 狀態 |
| ---- | ---- | -------------- | -------- | ------------ | ---- |
| Q-001 | [需要確認的產品或行為問題] | [spec、API 文件、設計稿或既有程式碼的內容] | [頁面、流程、API、權限或驗收項目] | [產品、設計、後端或使用者] | 待確認 |
```

問題應具體到可直接回答，不使用「細節待確認」等無法判斷影響的模糊描述。

### 11.3 優先級與阻擋範圍

```markdown
| 等級 | 定義 | 處理方式 |
| ---- | ---- | -------- |
| P0：整體阻擋 | 未確認前無法建立主要流程、頁面範圍或核心 API 契約 | SA 應明確標記，SD 不得自行假設 |
| P1：局部阻擋 | 只影響特定畫面、操作、狀態或次要 API | 可繼續處理不受影響部分，受影響內容保持待確認 |
| P2：可延後 | 不影響主要流程，可於後續補充或驗收前確認 | 記錄預期確認時點與影響範圍 |
```

優先級依「未確認會阻擋哪些工作」判定，不依問題看起來是否複雜判定。

### 11.4 確認後的更新規則

- 將確認結果更新到實際受影響的 SA 章節，不只修改待澄清表格
- 將項目狀態更新為「已確認」，並保留確認依據或決策來源
- 若確認結果影響流程圖、畫面狀態、API 契約、業務規則或權限，應同步更新相關內容
- 在 `sa-output.md` handoff 中列出仍未確認的項目及其阻擋範圍
- 不得只在對話、留言或 handoff 中保留最終答案，而讓 SA 正文維持過時內容

## 13. 完整情境範例

本章示範如何將前述規範整合為可供 SD 延伸的前端 SA 情境。範例中的 route、API 路徑、欄位與狀態值皆為占位內容，不代表真實契約；實際文件必須以 spec、Swagger／OpenAPI、設計稿與既有前端程式碼為依據。

### 13.1 情境範例模板

```markdown
### [編號] 情境[編號]：[情境名稱]

**流程說明：** [使用者執行什麼操作，以及預期得到什麼結果]

**前置條件：**

- [角色、權限、頁面或資料條件]

**觸發操作：**

- [進入流程的使用者操作]

**主要流程：**

​```
[使用者操作 → 畫面回應 → 資料互動 → 流程結果]
​```

**畫面狀態：**

| 狀態 | 畫面呈現 | 可用操作 |
| ---- | -------- | -------- |
| [適用狀態] | [內容或提示] | [允許的操作] |

**成功結果：**

- [內容更新、提示或導航結果]

**失敗結果與復原方式：**

- [錯誤呈現、保留內容與復原操作]

**業務規則與限制：**

- [影響內容、欄位、操作或流程結果的規則]

**SD 設計提示：**（可選）

- [需要 SD 進一步決定的技術問題]
```

時序圖只在外部 API、第三方服務、即時事件或複雜非同步順序會影響畫面結果時加入。

### 13.2 實際範例：載入與查詢課程列表

**流程說明：** 管理員進入課程列表，查看資料並透過搜尋或篩選縮小結果。

**前置條件：**

- 管理員已進入後台
- 管理員具有查看課程的權限

**觸發操作：**

- 從後台導航進入課程列表頁

**主要流程：**

```
管理員進入課程列表
  ├─> 顯示載入狀態
  ├─> 取得課程列表
  │   ├─> 有資料：顯示列表與可用操作
  │   ├─> 無資料：顯示空狀態
  │   └─> 失敗：顯示錯誤與重試操作
  └─> 管理員搜尋或篩選
      └─> 更新查詢結果與畫面內容
```

| 狀態 | 畫面呈現 | 可用操作 |
| ---- | -------- | -------- |
| 載入中 | 顯示列表載入狀態 | 依需求限制查詢操作 |
| 成功 | 顯示課程列表與查詢結果 | 搜尋、篩選或進入課程 |
| 空資料 | 顯示無課程或無符合結果 | 清除條件或執行已允許的建立操作 |
| 錯誤 | 顯示受影響範圍與失敗原因 | 重試或返回 |

**SD 設計提示：**

- 需設計查詢條件、分頁與畫面狀態的保存方式
- 需決定首次載入與局部查詢更新的技術處理

### 13.3 實際範例：編輯並儲存課程

**流程說明：** 管理員修改課程內容，通過欄位規則後送出並查看更新結果。

**主要流程：**

```
管理員進入課程編輯頁
  ├─> 載入既有內容
  ├─> 修改欄位
  │   ├─> 符合規則：允許送出
  │   └─> 不符合規則：顯示欄位錯誤
  └─> 點擊儲存
      ├─> 提交中：防止重複送出
      ├─> 成功：顯示最新內容與成功結果
      └─> 失敗：保留輸入並允許重新送出
```

**業務規則與限制：**

- 欄位限制必須以 spec、API 契約或已確認需求為依據
- 操作成功後的停留位置或導航結果必須明確
- 離開含未儲存內容的頁面時，其提示與結果必須有需求依據

**SD 設計提示：**

- 需設計表單狀態、驗證與 API 錯誤的整合方式
- 需設計成功後畫面資料同步方式

### 13.4 實際範例：無權限進入或操作

**流程說明：** 管理員進入頁面或執行操作時，前端依已確認的權限規則呈現可用內容與替代流程。

| 情境 | 畫面回應 | 導航結果 | 可用操作 |
| ---- | -------- | -------- | -------- |
| 無權限進入頁面 | 顯示已確認的提示或替代內容 | 返回或導向已確認頁面 | 重新登入或返回 |
| 無權限執行操作 | 隱藏、停用或拒絕後提示 | 維持目前頁面或依需求導頁 | 關閉提示或執行其他操作 |
| 業務狀態禁止操作 | 顯示停用原因 | 維持目前頁面 | 執行其他允許操作 |

**注意事項：**

- 隱藏、停用與拒絕後提示不可互相替代，必須依需求記錄
- 前端權限呈現只負責使用者體驗，外部 API 仍須執行真正授權

### 13.5 實際範例：第三方服務返回流程（選用）

**流程說明：** 管理員啟動第三方服務後離開目前頁面，完成、失敗或取消後返回前端並看到可預期結果。

```
管理員啟動第三方流程
  ├─> 前端顯示跳轉或等待狀態
  ├─> 進入第三方服務
  └─> 返回前端
      ├─> 成功：顯示完成結果並更新相關內容
      ├─> 失敗：顯示原因並提供重試或返回
      ├─> 取消：返回原流程或已確認位置
      └─> 未知結果：顯示安全提示並重新確認狀態
```

**SD 設計提示：**

- 需依第三方契約設計回傳結果辨識與重複回傳處理
- 需設計離開與返回期間的狀態保存及資料重新確認方式

```
步驟名稱
  │
  ├─> 子步驟 1
  ├─> 子步驟 2
  └─> 子步驟 3

```
[角色 A]                    [角色 B]
   │                           │

   │                           │

## 附錄 B：實用技巧

### B.1 如何組織複雜流程

**問題：** 流程太複雜，單一流程圖難以表達

**解決方案：**

1. **分層描述**：主流程 → 子流程詳細說明
2. **時序分離**：使用時序圖補充流程圖
3. **情境拆分**：將大情境拆分成多個小情境
4. **使用參照**：「詳見章節 X.X」

### B.2 如何處理並行流程

**問題：** 多個操作同時進行，難以線性表達

**解決方案：**

```
主流程
  │
  ├─> [並行處理]
  │   ├─> 並行操作 1
  │   ├─> 並行操作 2
  │   └─> 並行操作 3
  │
  ├─> [等待所有完成]
  │
  └─> 後續處理
```

### B.3 如何標示非同步操作

**問題：** 非同步操作的時序難以表達

**解決方案：**

```
使用者操作
  │
  ├─> 發送請求 (非同步)
  │
  ├─> 繼續其他操作
  │
  └─> (稍後) 收到回應
      └─> 處理結果
```

### B.4 如何呈現循環流程

**問題：** 需要表達重複執行的流程

**解決方案：**

```
開始輪詢
  │
  ├─> [每 5 秒執行一次]
  │   ├─> 檢查狀態
  │   ├─> 處理結果
  │   └─> 如果未完成，繼續輪詢
  │
  └─> 完成後停止
```
