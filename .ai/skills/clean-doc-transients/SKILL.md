## 功能需求

$ARGUMENTS

本 Skill 負責將目標 SA 或 SD 文件由「工單過渡狀態」清洗還原為「系統現役基線文件（Living Baseline）」：

### 階段一：SA / SD 共同通用清理（直接執行）

1. 掃描並移除所有歷史工單標籤（如 `[🆕 vX.X]`、`（本次新增）`、`[修改]` 等）
2. 掃描並刪除劃線墓碑行（`~~...~~`）與死屍代碼/檔案註解
3. 移除 Implementer 專屬任務步驟清單（如「建議實作順序 1~N」）
4. 檢查並移除 Scaffolding Q&A 對照表（如獨立臨時章節），確認核心結論已合流至內文
5. 檢查「版本歷史」章節：若單一版本說明過長（超過 3 行或混雜工單協商過程、細部條目流水帳），擷取核心架構里程碑與功能重點進行摘要提煉（壓縮至 1~3 行），確保簡潔
6. 重構檔頭為標準 Feature 基線格式（移除 Change ID、upgrade 模式偵測等暫態 metadata）

### 階段二：依文件型態差異化深入處理與 Grill-me 確認

- **若為 SA 文件（`*-sa.md`）**：
  - 堅守**純粹黑箱導向原則（SA 絕對不出現任何內部代碼與檔案路徑，由 SD 承擔所有程式碼映射）**。
  - 透過中性通用 prompt 啟動 **Grill-me 模式**，逐項與用戶確認代碼拔除、歷史痕跡撫平與佔位骨架守恆。
- **若為 SD 文件（`*-sd.md`）**：
  - 維持**白箱技術設計基線**（保留 Component、Hook、Storage 實體路徑與型別契約）。
  - 先直接執行 Implementer 便籤與原型參照撫平（不走 Grill-me 直接執行）。
  - 接續輸出中性 prompt 提供給用戶自行下達 `/grill-me`，逐項確認實作提示收斂、測試策略轉化為回歸基線、檔案清單純粹化等項目的刪減與縮減。

### 階段三：收尾驗證

- 自動重新對齊目錄（TOC）錨點；若 `package.json` 有定義 `format` script 則執行 `pnpm format` 格式化。

## 執行準則

- **角色**：文件減脂與去雜訊稽核員（Documentation Cleaner）
- **核心心法**：**只殺暫態雜訊，不殺架構規則與契約**。
- **章節骨架守恆原則（嚴禁整章刪除）**：
  - **在刪除內容時，如果剛好遇到整個章節的內容都可以刪除，請一定要保留原始章節標題（H2 / H3）**。
  - **絕對不可連同標題將整章拔除**，避免破壞 SA/SD 的標準架構規範、導致章節跳號、破壞目錄（TOC）結構與交叉參照。
  - **核心目的（重要）**：**保留章節 Title 作為標準結構錨點，以便下次執行 Change 流程（如 `sa-writer` / `sd-writer` 於 upgrade 模式時）能精準定位並生成／擴充至正確的章節位置**，避免因章節缺失導致結構錯位、順序混亂或由零誤判重寫。
  - **清空後的內文處理**：保留原始章節標題，並在內文補上一行客觀宣告或合流說明（例如：`> 本模組不涉及此項目，故本章不適用。` 或 `> 目前無未結案之待澄清事項，所有決議已合流至正文各章。`，情境級別則以 `- 無` 佔位）。
- **不可誤殺保護白名單（Safety Invariants）**：
  - **原始章節標題與結構骨架**（100% 保留章節標題；遇整章內容可刪除時，標題必須保留並標註不適用，嚴禁整章拔除造成跳號）
  - **ADR 架構決策與偏離常規之理由**（100% 保留）
  - **路由邊界約束與隔離原則**（100% 保留）
  - **TypeScript 資料模型與業務契約**（View Model、Form Values 型別定義與業務驗收標準 100% 保留）
  - **錯誤處理與畫面狀態矩陣**（100% 保留）
  - **版本歷史架構里程碑**（保留歷代版本演進；單一版本說明超過 3 行時提煉為 1~3 行重點摘要）
- **合流優先**：若被清理的段落含有未合流的架構規則，必須先將規則補寫入對應章節，方可刪除該段落。

## Step 1：取得目標文件與預檢

### 檢查 1：解析文件路徑

- 若 `$ARGUMENTS` 有指定路徑：使用該路徑（如 `docs/features/member/member-sd.md` 或 `docs/features/member/member-sa.md`）
- 若未指定：檢查 `docs/changes/_active.md`，若有 active change 則提示或預設處理該 change 下的 `sd.md`／`sa.md`；若無則提示用戶指定檔案路徑。

### 檢查 2：辨識文件類型分流

- 檢查檔案副檔名與命名結尾：
  - 若為 `*-sa.md`：標記為 **SA 模式**（需走階段二 Grill-me 流程）。
  - 若為 `*-sd.md`：標記為 **SD 模式**。

## Step 2：執行階段一 — SA/SD 通用暫態雜訊清理

在進行深層確認前，先自動執行以下 6 項通用清理：

1. **檔頭重構**：
   - 改為標準 Feature 基線頭部資訊（移除 Change ID、upgrade 模式說明等）：
     ```markdown
     # [SA/SD]：[模組名稱]（[模組英文代號]）— [功能涵蓋範圍簡述]

     > **版本：** vX.X
     > **更新日期：** YYYY-MM-DD
     > **文件類型：** [前端功能 SD 文件（模組基線文件） / 前端系統分析與行為設計文件]
     > **目標模組：** [模組代號]
     > **涵蓋範圍：** [核心頁面與功能條列]
     ```
2. **全文清除暫態增修標籤**：
   - 正則：`\[🆕\s*v?\d+(\.\d+)?\]`、`\[新增\]`、`\[修改\]`、`（本次新增）`、`（本次修改）`、`（vX.X 既有部分）`、`（本次刪除）` 等標籤剃除，還原為客觀陳述。
3. **刪除劃線墓碑與任務步驟清單**：
   - 刪除純歷史劃線行（`~~...~~`）；移除「建議實作順序 1~N」步驟清單。
4. **移除或佔位處理 Scaffolding 協商章節**：
   - 獨立的臨時 Q&A 章節在確認合流後依骨架守恆規範清理。
5. **版本歷史精簡與重點摘要（超過 3 行優化）**：
   - 檢查「版本歷史」章節：
   - 單一版本說明若超過 3 行，或混入工單協商過程（如「依 handoff/clarifications 逐項確認」、「Q-xxx 回寫」），提煉為 **1 ~ 3 行** 之核心架構里程碑與功能交付摘要；同一版號之多筆臨時修訂列予以合併。

## Step 3：執行階段二 — 差異化深層處理與 Grill-me

### 【SA 文件專屬】純粹黑箱導向與 Grill-me 互動確認

當目標文件為 SA 時，Agent **必須透過 Grill-me 方式** 向用戶條列發現並確認下列 5 個中性維度的修訂：

#### 1. 內部代碼與路徑清理（去代碼化維度）

- **核心準則**：**SA 絕對不出現任何內部代碼與檔案路徑，由 SD 承擔所有程式碼映射**。
- **掃描特徵**：
  - 前端程式碼路徑：`src/app/...`、`src/hooks/...`、`src/lib/...`、`src/api/generated/...`。
  - 具體 Component 與 Hook 名稱：如 `useCurrentMember`、`LearningChapterFab`、`PdfPageControls`。
  - 後端程式碼細節：Prisma / DTO Class 名稱、內部 Service 名稱（如 `EmailSendCooldownService`）、Git commit 哈希（如 `commit 7ce3090`）。
- **Grill-me 提案**：
  - 將內部實體轉譯為純黑箱業務與行為規範（例如：將 `src/hooks/use-login-redirect-guard.ts` 轉為「全域統一登入守門機制」；將 `UpdateMemberProfileDto` 轉為「系統允許長度上限」；將 API 生成路徑還原為純 REST 契約 `METHOD /path`）。

#### 2. 過渡期與 Changelog 語氣撫平（Living Baseline 維度）

- **核心準則**：SA 是系統現役狀態的唯一真相來源（Single Source of Truth），非歷史工單修訂日誌。
- **掃描特徵**：「原本是 A 本次改成 B」、「沿用 v1.x 基礎」、「本次為擴大套用範圍非新增機制」、「（不再有某畫面狀態）」等工單對比敘述。
- **Grill-me 提案**：撫平為客觀現況規格，直接陳述系統目前的真實行為。

#### 3. SD 設計提示的處理（骨架守恆維度）

- **核心準則**：**各情境末端的 `**SD 設計提示：**` 標題 100% 保留，內文清空並填寫 `- 無`**。
- **說明**：情境中的 SD 提示屬於當下交辦給 SD 的臨時便籤，實作完成歸檔後已在 SD 與代碼定案。保留標題可維護規範骨架與 TOC 完整性，且**確保下次執行 Change 流程時，AI 能直接在此標題下方生成新情境的技術提示**，清空內文則徹底排除過時雜訊。

#### 4. 待澄清事項骨架守恆

- **核心準則**：保留待澄清事項 H2 標題，內文清空整張 `Q-xxx` 歷史問答表格，改以標準佔位宣告：
  ```markdown
  > 目前無未結案之待澄清事項，所有決議已合流至正文各章。
  ```
  **目的**：保留 H2 錨點，以便下次 Change flow 時，`sa-writer` 若有新產生的待澄清問題能直接生成至本章，避免章節遺失。
- 正文中引用的暫態工單路徑（如 `handoff/clarifications.md`）一併清洗為客觀業務依據或移除失效參照。

#### 5. 非功能性需求與原型參照客觀化

- **核心準則**：
  - 將「本次不加錯誤追蹤」等臨時工單限制，改寫為「全站目前未整合前端錯誤追蹤與事件埋點」客觀現況。
  - 將正文引用的過渡 HTML 原型檔名（如 `user-my-courses.html`）改寫為具體 UI 規格描述或 Figma 設計稿參照。

### 【SD 文件專屬】技術實作基線維護與 Grill-me 互動確認

當目標文件為 SD 時，清洗流程分為「**SD 前置自動清理（直接執行，不走 Grill-me）**」與「**輸出中性 Prompt 供用戶下達 Grill-me 確認**」兩階段：

#### 階段 A：SD 專屬過渡期便籤與原型參照撫平（直接執行，不走 Grill-me）

除通用清理（工單標籤、劃線墓碑、Q&A 協商對照表佔位清空、版本歷史精簡）已由階段一自動完成外，此處僅需直接執行 SD 專屬之過渡內容撫平：

1. **移除 Implementer 臨時提示框**：全數移除 `> ⚠️ 給 Implementer：...` 便籤框，將其具長效架構約束價值的規格（如版面佈局比例、Token 約束）自然融入正文技術規格描述。
2. **原型檔名與工單對比語氣客觀化**：移除 `user-*.html` 等過渡期靜態原型檔名參照，改為客觀 UI 規格描述或 Figma 設計稿參照；撫平「原本是 A 本次改為 B」等工單對比敘述。

#### 階段 B：輸出中性 Prompt 提供用戶自行下達 Grill-me 確認

完成階段 A 前置自動清理後，**Agent 不得擅自整段刪除具技術價值的章節**（因每份 SD 之章節結構與編號各自不同，不可硬編碼特定章節）。
Agent 必須分析該份 SD 的實際結構，並**向用戶輸出結構化之中性 Prompt 範本**，明確要求分析歷史實作資訊，區分出「可刪除的過渡流水帳」與「不可刪除的核心架構決策」，由用戶自行下達 `/grill-me` 指令逐題確認：

##### 輸出給用戶的中性 Prompt 範本：

```text
/grill-me 請深入分析本份 SD 文件的歷史實作內容，區分「過渡性實作流水帳（可刪除）」與「核心架構決策（不可刪除）」，並依據以下 3 大語意維度逐題與我確認哪些內容需要刪除、合流或縮減：

1. 實作提示與任務步驟結構收斂：
   - 區分「長效架構防雷決策（不可刪，保留）」與「實作期驗證清單（具長效約束者合流，其餘清空佔位）」。
   - 清空工單專屬之「建議實作順序」（保留標題佔位），宣告基線功能已實作完成。
2. 驗收與測試策略轉化為回歸基線：
   - 移除「本 change 不新增測試檔」等工單過渡語氣。
   - 區分單次工單測試備忘（可刪）與模組核心測試切分/驗收清單（不可刪，保留並確立為功能回歸驗收基線）。
3. 檔案架構清單純粹化與解耦：
   - 區分「模組檔案架構職責（不可刪，保留）」與「代碼 diff 行號/TODO 流水帳（可刪，剔除）」。
   - 將環境依賴、套件安裝等建置紀錄收斂至 ADR 架構決策表。
```

#### 階段 C：Grill-me 逐項互動確認機制（歷史實作 vs 架構決策判別基線）

當用戶啟動 Grill-me 流程時，Agent **必須先掃描全篇技術實作資訊**，嚴格依據「**歷史實作（可刪除） vs 架構決策（不可刪除）**」的核心界線逐題提問：

##### 核心判別原則（不可誤殺白名單）

- **核心架構決策（絕對不可刪除，Safety Invariants）**：
  - 凡涉及 ADR 技術選型依據、跨模組/路由邊界約束、SSR/CSR 渲染邊界、快取過期重取防迴圈機制、記憶體防護（如 Blob 生命週期、canvas 渲染限制）、型別契約與全域守門邏輯者，**皆屬於核心架構決策，100% 必須保留**；若原散落於實作期驗證章節中，必須提煉合流至高風險設計點或正文規格，嚴禁誤刪。
- **歷史實作流水帳（可刪除 / 縮減 / 佔位清空）**：
  - 凡僅供特定工單執行時期的步驟順序（1~~N）、代碼修改行號（如「約第 49~~51 行」）、臨時 TODO 備忘、過渡性 patch 說明、已驗收完成之單次檢查項，**皆屬於歷史實作雜訊，確認無殘留架構決策後應予刪除、清空或提煉為客觀職責**。

##### Grill-me 訪談提問規範

Agent 在逐題向用戶提問時，**必須主動向用戶說明判定理由**：

- 範例：「針對此項驗證點『PDF 單頁渲染與大檔記憶體防護』，因涉及記憶體防護之核心架構決策，建議合流至高風險設計點而非直接刪除，您同意嗎？」
- 範例：「針對此檔案說明中的『第 49~51 行 TODO 註解』，屬於特定工單代碼 diff 流水帳，建議還原為客觀架構職責描述，您同意嗎？」

##### 3 大中性維度確認要點（語意維度，無寫死章節號）

###### 1. 實作提示與任務步驟結構收斂（語意維度）

- **核心準則**：保留長效架構防雷指南，清空工單期臨時執行步驟，嚴格遵守骨架守恆保留標題。
- **動態辨識**：文中包含「高風險設計點」、「建議實作順序」、「實作期驗證清單」等技術提示小節（章節編號因文件而異）。
- **Grill-me 確認要點**：
  - **高風險設計點**：100% 保留，作為長期的技術防雷與邊界約束指南。
  - **實作期驗證清單**：提取具長期架構約束價值（如 SSR hydration 防護、並行競爭、快取與記憶體防護）之項目合流至高風險設計點；合流後依骨架守恆保留標題，內文清空並填寫佔位說明（例如：`> 實作驗證重點已合流至高風險設計點，無其他未決事項。`）。
  - **建議實作順序**：純屬工單執行期步驟，依骨架守恆保留標題，內文清空並填寫佔位說明（例如：`> 本模組基線功能已實作完成，無待執行實作順序。` 或 `- 無`）。

###### 2. 測試策略轉化為長期回歸驗收基線（語意維度）

- **核心準則**：將工單驗收便籤轉化為系統長期演進的回歸測試基線（Regression Baseline）。
- **動態辨識**：文中包含「模組驗收與測試指引」、「單元測試切分」、「核心驗收清單」等測試章節（章節編號因文件而異）。
- **Grill-me 確認要點**：
  - 移除工單過渡語氣（如「本 change 不新增測試檔」、「TODO 已移除」、「建議未來補測」等）。

  - **核心驗收清單**：保留並改寫為客觀的「功能回歸驗收清單（Regression Checklist）」，作為未來模組修改時的回歸測試與驗收標準。
